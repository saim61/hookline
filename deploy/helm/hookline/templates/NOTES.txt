{{- if .Values.migrations.enabled }}

The schema was migrated by a pre-upgrade hook Job before these pods started. What it did:

  kubectl logs -n {{ .Release.Namespace }} job/{{ include "hookline.fullname" . }}-migrate
{{- else }}

WARNING: migrations.enabled is false, so no schema upgrade ran. The pods will start and fail
readiness against a database that may be missing tables. Run it yourself:

  kubectl run -n {{ .Release.Namespace }} migrate --rm -it --restart=Never \
    --image={{ include "hookline.image" . }} -- alembic upgrade head
{{- end }}

Create the first API key. This has to happen against the database rather than over HTTP,
because minting a key requires a key:

  kubectl exec -n {{ .Release.Namespace }} -it \
    deploy/{{ include "hookline.fullname" . }}-api -- \
    hookline-admin create-key --name "bootstrap"

{{ if .Values.api.ingress.enabled -}}

{{- if .Values.config.dashboardEnabled }}

{{- else -}}
No ingress. To reach it locally:

  kubectl port-forward -n {{ .Release.Namespace }} \
    svc/{{ include "hookline.fullname" . }}-api {{ .Values.api.service.port }}:{{ .Values.api.service.port }}

  curl localhost:{{ .Values.api.service.port }}/ready
{{- if .Values.config.dashboardEnabled }}
  open http://localhost:{{ .Values.api.service.port }}/dashboard
{{- end }}
{{- end }}

Watch whether delivery is keeping up. This one number answers it - if it grows, add worker
replicas; they coordinate through Postgres, so no configuration changes:

  max(hookline_oldest_pending_delivery_age_seconds)
